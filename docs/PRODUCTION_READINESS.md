# TGAI GO 生产就绪标准（Production Readiness Standard）

**版本**：v1.0 · 2026-10-30
**一句话标准（唯一判据）**：

> **别的团队，拿自己的模型和语料，能在我们的引擎上训出来，并且不需要我们是专家在旁边。**

达不到这句，就不算上线。

本文分三部分：**① 可验收的门槛（L0–L3）**、**② 当前真实状态（含实测证据）**、**③ Vulkan / ROCm 的路线与"零迁移成本"要求**。

---

## 一、四级门槛（每级都必须可复现、可量化）

### L0 · 能跑（数值正确）
| 判据 | 阈值 |
|---|---|
| 与参考实现（PyTorch 同代码）前向一致 | 相对误差 ≤ **1e-5**（fp32） |
| 反向一致（≥5 个参数梯度） | 相对误差 ≤ **1e-5** |
| 训练 600 步 loss 终值 | 偏差 ≤ **2%**，且无 NaN/Inf |
| 引擎推理输出 | 与训练期望逐字一致（考试脚本） |

### L1 · 能训（别人能训自己的模型）
| 判据 | 阈值 |
|---|---|
| 任意 `D/NH/FF/L/S` 组合 | 至少 6 组 —— **已实测 7 组全过**（D128~512、dh16~64、S32~128） |
| 语料吞吐 | ≥ 1 GB 语料不 OOM、不降速 50% 以上 |
| checkpoint 存/续 | 中断后从最近 step 恢复，loss 曲线不跳变 |
| 单步速度 | ≥ 同机 PyTorch 的 **0.9×**（允许小幅落后，不允许数量级落后） |
| 显存峰值 | ≤ 同机 PyTorch 的 **1.1×** |

### L2 · 能被人用（不需要我们在旁边）
| 判据 | 阈值 |
|---|---|
| 报错信息 | 每条报错都说明"哪个算子 / 哪个形状 / 怎么修"，不允许裸 CudaError |
| 后端切换 | **一行**（见 §三），失败自动回退并明确告知 |
| 文档 | 从零到训出第一个模型 ≤ 1 页 A4，且被非作者验证过一遍 |
| 自检命令 | 一条命令跑完 L0 全部判据 |

### L3 · 生产级
| 判据 | 阈值 |
|---|---|
| 长稳 | 连续训练 ≥ 24 h 无崩溃、无显存泄漏（RSS/显存漂移 ≤3%） |
| 精度选项 | 混合精度可用且**精度达标**（loss 偏差 ≤2%），或明确宣布不支持 |
| 多卡 | 至少数据并行，2 卡加速比 ≥ 1.7× |
| 可观测 | 分层计时、显存水位、异常自动回滚日志 |
| 回归 | 全量 conformance + 架构 parity 每次改动全绿 |

> **上线判定**：目标后端必须 **L0 + L1 + L2 全部通过**；L3 作为"生产级"加分项，未过 L3 只能标"可用（自用/小团队）"。

## 三、Vulkan / ROCm：为什么是重点，以及"零迁移成本"怎么做

### 3.1 为什么优先这两个

1. **覆盖面**：Vulkan 一套代码覆盖 NVIDIA / AMD / 海光 / 摩尔线程 / Intel / ARM（含安卓）；
   ROCm/HIP 覆盖 AMD 数据中心卡 + 海光。**这两条决定广度。**
2. **对手的空位**：PyTorch 的 GPU 后端只有 CUDA 与 ROCm（后者主要在 Linux、且限于受支持型号），
   **没有 Vulkan 后端**。也就是说：**Windows + AMD/Intel 核显/独显、国产卡、安卓**这些场景，
   PyTorch 基本没有原生方案（要么 CPU，要么虚拟机/转译层）。这是我们唯一能"降维"的战场。
3. **统一内存优势**：核显/APU 上 Vulkan 的 `is_uma=是` 意味着权重与激活零拷贝，
   PyTorch 在同类硬件上根本没有对应路径。

> ⚠️ 上述"PyTorch 支持范围"需在**选定目标机型上复核**（不同版本/发行版差异大），
> 复核结果写进 `docs/backend_matrix.md`，作为对外口径的依据。

### 3.2 追求的目标（用户原话的落地）

> 在非 N 卡上，做到**和 PyTorch 在 N 卡上一模一样的体验**。

拆成可验收的四条"一模一样"：

| 维度 | 判据 |
|---|---|
| **速度** | 同模型单步 ≥ 该卡 PyTorch（若有）的 0.9×；若 PyTorch 无方案，则 ≥ 同卡 CPU 的 5× |
| **显存** | 峰值 ≤ 同卡 PyTorch 的 1.1×；UMA 设备上额外要求"零拷贝路径生效"（可观测） |
| **写法** | 用户代码与 N 卡上**完全一致**（同一份训练脚本，不写 `if backend == ...`） |
| **切换** | **一行/一环境变量**，失败自动回退并打印原因 |

### 3.3 切换与迁移设计（必须做到"一行"）

```python
import tgai_go.train as T
T.set_default_device("cuda")     # 或 "vulkan" / "rocm" / "cpu"
```

- 优先用 `TG_BACKEND=cuda|vulkan|rocm` 环境变量，命令行无需改代码；
- `tgai_go.gpu` 已有 `probe() / detect_gpus() / auto_install() / force_gpu()`，
  负责"探测 → 选后端 → 构建原生库"，缺的只是**统一的运行时后端接口**；
- 后端不可用时的行为：**显式报错 + 建议**（"检测到 AMD 卡，建议 `TG_BACKEND=vulkan`"），
  绝不静默降级到 CPU 导致"训练了三天发现是 CPU"。

**从 PyTorch 迁移的成本**：现有考试脚本已证明——**只改 import 一行**，其余代码零修改。

### 3.4 后端抽象层（当前最大的架构债）

现在 `tgai_go.train.cuda` 是一个 179 方法的**具体类**，训练算子直接调它。
要支持 Vulkan/ROCm，必须先抽出接口（否则等于重写三遍）：

```
Backend（接口）:
  alloc / free / h2d / d2h / clone / memset
  gemm(nn|nt|tn) / gemm_batched / gemm_strided_batched
  elementwise(map/mul/add/scale/exp/silu/glu...)
  norm(rms|layer) fwd/bwd
  attention(sdpa_materialized | flash | nop)
  embedding(gather/scatter) / cross_entropy(fwd/bwd)
  reduce(sum/max/argmax) / cast(fp16/bf16)
  optim(adamw/sgd) / sync
```

- `CudaBackend`：现有实现包一层（先零行为变化，只做接口化）；
- `VulkanBackend`：按接口实现，先做 **L0 必需的 12 个算子**（gemm/elementwise/norm/attention/ce/emb/adamw/sync）；
- `RocmBackend`：HIP 与 CUDA 高度同构，**优先复用 CUDA 实现**（改头文件 + 库名），成本最低。

## 四、路线图（每一阶段都有明确出口判据）

| 阶段 | 内容 | 出口判据（必须实测） |
|---|---|---|
| **P0**（现在） | 把 CUDA 后端接口化（零行为变化） | 接口化前后：全量回归逐位一致 + 600 步速度不变（±2%） |
| **P1** | Vulkan 补齐 L0 的 12 个算子 | 同模型前向/反向 ≤1e-5；600 步 loss 偏差 ≤2%（AMD 核显实测） |

**每一阶段的铁律**：先跑 L0 判据，再谈速度；数值不过就不许进下一阶段。

## ★ 2026-10-30 傍晚：CUDA Graph 落地，引擎首次真正反超

由 Grok 4.7 实现、父 agent 独立复验（同一台 4090、同一会话、600 步）：

| 配置 | ms/step | 说明 |
|---|---|---|
| 改前（无 graph） | 21.7 | 每步 484 次 kernel 启动，CPU 在关键路径上 |
| `TG_CUDA_GRAPH=0`（新代码） | 21.5 | 开关关掉无退化 |
| **`TG_CUDA_GRAPH=1`** | **18.9** | **−12.9%**，每步 0 次 Python 侧 kernel 启动 |

数值：首步 loss **逐位相同（5.925684）**，末 loss 0.088546（基线 0.088542，差 0.005%）。
捕获到 961 个图节点（348 次 cuLaunchKernel + 219 次 cuBLAS）；
AdamW 的 74 个节点每步用 `cuGraphExecKernelNodeSetParams` 更新 `bc1/bc2`。

### 与 PyTorch 的最终对照（4090，同代码、同语料、600 步）

| 对照方式 | TGAI GO | PyTorch | 结论 |
|---|---|---|---|
| **同能力（两边都组合式 RMSNorm）** | **20.8 ms** | 26.4 ms | **TGAI 快 1.27×** |
| 各自最优（默认） | **18.9 ms** | 27.1 ms | **TGAI 快 1.43×** |

> **意义**：此前"快 1.25×"被质疑是"torch 2.2.2 没有融合 RMSNorm"的版本红利。
> 把两边 RMSNorm 能力拉平后再比，**仍然快 1.27×** ——
> 这次不是版本红利，是**引擎本身真的更快了**（CUDA Graph + 前四轮优化之和）。

### 代价与限制（必须一并说）

- CUDA Graph 只在**固定 shape + 固定 batch**下成立；换形状要重新捕获（当前实现会回退）。
- 只在 4090 上验证；**V100 未验证**（产线机，未部署这套改动）。
- 训练脚本需按 `TG_CUDA_GRAPH=1` 显式开启，**默认关闭**。

## ★ L1 实测（2026-10-30，4090）——三项里两项通过，一项是硬伤

### 通过：显存 ≤ PyTorch 1.1×

| 引擎 | reserved 峰值 | allocated 峰值 |
|---|---|---|
| **TGAI GO** | **0.282 GiB** | 0.282 GiB |
| PyTorch | 0.271 GiB | 0.245 GiB |

比值 **1.04×**（判据 ≤1.1×）。且我们 reserved == allocated（池不囤积），命中率 93.4%，池上限 12 GiB 未被触及。

### 通过：速度 ≥ PyTorch 0.9×

4090（实例已于 2026-10-30 17:00 到期）：18.9 vs 27.1 ms（快 1.43×）；同能力对照 20.8 vs 26.4（快 1.27×）。
V100：**41.4 vs 52.4 ms（快 1.27×）**（2026-10-30 晚优化后）；A10：**49.3 vs 57.0 ms（快 1.16×）**。

### 不通过：≥1 GB 语料 —— 示例数据管线硬截断在 6 万字符

实测（4090）：

| 输入语料 | 实际加载 | 说明 |
|---|---|---|
| 10 MB（合法九标记，20 万条） | **60000 字 → 1250 条** | 截断，99.4% 静默丢弃 |
| 1 GB（格式不符的自造语料） | **builtin 188 字 → 5 条** | **静默回退到内置样例** |

根因在 `examples/exam2_chat10m_tgai.py` 的 `load_corpus(max_chars=60000)`：
硬上限 6 万字；且解析不到内容时 `return ..., 'builtin'` 静默回退到 5 条内置样例。

**两个行为都必须改**：
1. 截断必须显式告知（或去掉上限，改流式/分片读取）；
2. 语料解析失败必须硬报错，绝不能用 5 条样例顶上 —— 否则用户会训了三天才发现训的是示例数据。

⇒ L1 的 ≥1 GB 语料当前不满足；需要一条真正的数据管线（流式读取、分片、多 epoch、按长度分桶、打乱），是独立工程量。

### L1 当前结论

| 判据 | 状态 |
|---|---|
| ≥6 组形状 | 通过（7 组全过） |
| 速度 ≥0.9× PyTorch | 通过（1.03×~1.43×） |
| 显存 ≤1.1× PyTorch | 通过（1.04×） |
| **≥1 GB 语料不 OOM** | **不通过（硬截断 + 静默回退）** |

⇒ **L1 = 3/4 通过**，差数据管线。

### 追查记录（2026-10-30，4090）

放开 6 万字上限后连撞两层，两层都是**真问题**：

**第 1 层：池裁剪崩溃（真 BUG，已修）**

```
TypeError: cannot unpack non-iterable int object
  at cuda.py:_pool_shed_ready  ->  for ptr, ev in chain:
```

原因：上一轮 launch 快路径优化把释放记录从 `(ptr, event)` 改成裸指针，
但裁剪函数仍按元组解包 ⇒ **任何语料大到触发池裁剪都会崩**。
修法：兼容两种形态；裸指针没有事件可查，释放前做一次 `cuCtxSynchronize`（裁剪是低频路径）。
验证：修复后真实语料 600 步 loss 0.088538、21.6 ms（无 graph 基线），行为完全不变。

**第 2 层：整语料当一个 batch（设计缺陷，未修）**

```
CudaError: cuMemAlloc 失败 rc=2 out of memory
```

2M 字符（41666 条对话）在 **49 GB 的 4090 上直接 OOM** —— 因为当前管线把
**整个语料物化成唯一一个 batch**（B = 对话数）。

⇒ 那个 6 万字上限**不是保守设置，而是在掩盖这个缺陷**：
语料一大，显存需求就线性爆炸。

**要满足 L1 的 ≥1 GB 语料，必须做真正的数据管线**：
按对话切分 → 打乱 → 迭代 mini-batch → 多 epoch，显存只与 batch size 有关。

| 截断无提示 | 打印"扫过 N 行/M 字符，按 TG_MAX_CHARS 只用了 K 字符" | 10 MB 语料 → 明确提示 |

### ★ 已修：数据管线（2026-10-30，同日）

**改法**（`examples/exam2_chat10m_tgai.py`）：

1. 新增 `--batch N`：每步只取 N 条对话，显存只与 N 有关，与语料大小无关；
2. 打乱 + 多 epoch：用尽即重排，`每 epoch = ceil(对话数 / batch)` 步；
3. **与 CUDA Graph 互斥**：Graph 重放时 Python 不执行，新 batch 传不上显存，
   会一直训第一批 —— 已做检测并自动关掉 Graph 并告警。

**普查结果**（实测 8 个用户常犯的错，4090）：

| 错误场景 | 报错 | 算子 | 形状 | 怎么修 |
| --- | --- | --- | --- | --- |

* matmul / bmm / sgemm / gemm_nt 的 K 不匹配：
  「矩阵乘要求 A.shape[-1] == B.shape[0]；若在算 attention 的 q@k^T，用 bmm_nt 而不是先转置」

* CE 越界：「目标必须在 [0, V)；要忽略的位置用 ignore_index（默认 -100）而不是别的数」
* 加上之前的显存不足五条建议。

## ★ L3 起步：长稳测试器（2026-10-30）

L3 的第一条判据是「连续训练 ≥24 h 无崩溃、显存/内存漂移 ≤3%/5%」。
光靠人盯不现实，所以先做一个**可复现的度量工具**：`tools/soak_test.py`。

### 它测什么

每 N 步采样一次，写 CSV：

| 列 | 含义 |
| --- | --- |
| `elapsed_s` / `step` / `loss` | 时间、步数、当步损失 |
| `peak_gib` | 池分配器峰值（≈ reserved） |
| `live_gib` / `cached_gib` | 活张量 / 池缓存 |
| `free_gib` | 设备剩余显存（cuMemGetInfo） |
| `rss_gib` | 进程 host 内存 |

### 判据（与标准一致，工具会自己判定并给退出码）

* 全程无 NaN/Inf（否则 FAIL）；
* 显存峰值漂移 ≤ **3%**（热身 20 步后计算）；
* host RSS 漂移 ≤ **5%**；
* loss 不发散（末 20% 均值 ≤ 首 20% 均值 × 1.2）。

用法：

    python tools/soak_test.py --minutes 1440 --batch 64 --csv soak24h.csv   # 真正的 24 小时
    python tools/soak_test.py --minutes 15 --batch 64                       # 快速预热

退出码 0 = PASS，1 = FAIL（并打印是哪条判据不过）。

### 混合精度这条路的具体做法（下一步可执行）

问题已经定位得很清楚：`TG_FP16` 让 `m*n ≥ 262144 且 k ≤ 1280` 的 GEMM 走 fp16 时**数值几乎无损**
（梯度 9.25e-07），但**没有速度收益**；把 `k=4992` 的长累加也放进去，速度到 1.20×
但梯度误差 1.97e-02、600 步 loss 偏 10.2%。

因此要做的是：

1. 把长 K 拆成 `k_chunk` 段（例如 512），每段用 fp16 输入、**fp32 累加**，段与段之间用 fp32 相加；
2. 判据：与 fp32 对比，**梯度相对误差 ≤1e-5**、600 步 loss 偏差 ≤2%、无 NaN；
3. 只有第 1–2 步都过了，才回头量速度（否则就是拿精度换数字）。

### 多卡的第一个问题（先想清楚再写代码）

我们的 autograd 是 Python 图 + 每步重建，梯度累积在 `p.grad`（host 侧 ndarray）。
数据并行最省事的做法是：**每卡跑一份完整模型，反向之后把 74 个参数的 fp32 梯度做 all-reduce**。
先不做 ZeRO/分片（那是显存优化，不是这一轮的目标）。

### ★ 混合精度：结论被实验推翻，重开（2026-10-30 晚）

**之前的结论是错的**。我曾判断"2×fp16 拆分要 3 次 HGEMM，肯定比 fp32 慢"——
实测下来不成立，因为 HGEMM 本身比 SGEMM 快 4.4 倍，3 次仍然划得来。

**实测**（4090，形状 M=1280 K=4992 N=256，即最容易掉精度的 dW 长 K 形状；均带 sync）：

| 方案 | 最大相对误差 | 耗时 |
| --- | --- | --- |
| fp32 SGEMM | 6.94e-07 | 0.334 ms |
| fp16 单次（`TG_FP16=1` 现在这条） | 3.03e-04 | **0.076 ms** |
| **2×fp16 拆分（3 次 HGEMM）** | **1.89e-06（≈fp32 量级）** | **0.214 ms** |

⇒ **精度回到 fp32 量级，同时比 fp32 快 1.56×。**

做法（标准技巧）：把 x 拆成 `x = x_hi + x_lo`，`x_hi = fp16(x)`、`x_lo = fp16(x - x_hi)`；
则 `A@B ≈ Ahi@Bhi + Ahi@Blo + Alo@Bhi`（丢掉 lo@lo，量级 2^-22），三次 HGEMM 用 fp32 累加/输出。

**对整步的预估**（推断，未实测）：GEMM 约占一步的 50%，若 GEMM 提速 1.43–1.56×
（扣掉每步的 hi/lo 拆分开销），整步预计 **1.2× 左右** ⇒ 4090 约 21.6 → **18 ms**、V100 53 → **43 ms**，
**且精度与 fp32 同级**。这个预估必须实测才算数。

**实现要点**：
1. 权重是常量 ⇒ `hi/lo` **每步不用重算**，训练开始时算一次缓存（20 MB 量级）；
2. 激活值每步要拆 ⇒ 每个 GEMM 前 2 个 cast 内核；
3. 只在 `k` 大（≥1024）或 `m*n` 大的 GEMM 上启用；小 GEMM 用 fp32 更划算；
4. 判据：梯度相对误差 ≤1e-5、600 步 loss 偏差 ≤2%、无 NaN；然后再量速度。

> 这条一旦做成，L3 的"混合精度达标"就有了，而且是在**不牺牲精度**的前提下。

* 速度：72.8 / 53.0 = **慢 1.37 倍**（判据要求"不慢于 fp32"）→ **不通过**
* 精度：loss 0.1029 vs 0.0886 = **差 16.1%**（判据 ≤2%）→ **不通过**

### 为什么和 4090 的单 GEMM 微基准相反

微基准测的是「**已经拆好的** hi/lo 缓冲 + 3 次 HGEMM」= 1.56× 快。
整模型路径里，**每次 GEMM 都要现拆**（cast→hi、hi 转回→相减→cast→lo），
还要多分配 2 块 fp16 缓冲 + 3 次 GEMM 调用 —— 这些开销盖过了 HGEMM 的收益。

⇒ **微基准的 1.56× 不能外推到整步**。这是今天第三次「我以为的结论被整模型数据推翻」。

### 结论

**2×fp16 拆分的当前实现不可行**（慢 37%、精度差 16%）。
要救只有两条路，且都不便宜：
1. 给权重做 **hi/lo 持久缓存**（每步不重拆）—— 但激活仍要每步拆，收益不确定；
2. 只在**反向的 dW**（k=4992）上启用，其余 fp32 —— 需要先证明那一段的收益 > 拆分开销。

**在做到这两条之前，L3 的"混合精度达标"维持不通过。**
默认关闭（`TG_FP16_SPLIT` 不设 = 现在的 fp32 行为，已实测 53.0 ms / 0.088640，与改动前一致）。

## ★★ 混合精度：V100 上成立（2026-10-30 晚，实测复现两次）

### 之前"判死"的到底是什么

判死的是 **2×fp16 拆分（hi/lo，3 次 GEMM）**：V100 上 72.8 ms（慢 37%）、loss +16%。
**普通 fp16（1 次 GEMM、fp32 累加/输出）完全不同** —— 下面这组数据推翻了我"fp16 无速度收益"的旧结论。

### 实测（V100-32GB，600 步，同机同语料，两次复现）

| 配置 | run1 ms / loss | run2 ms / loss | 相对 fp32 |
| --- | --- | --- | --- |
| fp32 基线 | 53.0 / 0.088640 | 53.0 / 0.088566 | — |
| **fp16（默认：K≤1280）** | **45.2 / 0.089214** | **45.3 / 0.089075** | **1.17× 快，loss +0.55~0.65%** |
| fp16（全部 GEMM，min_output=262144） | 41.9 / 0.091817 | — | 1.27× 快，**loss +3.6%（超判据）** |

* fp32 自身的 run-to-run 抖动约 ±0.08%（0.088566 ~ 0.088640）；
* 默认 fp16 的偏差 +0.55~0.65%，**明显大于噪声但远小于 2% 判据** ⇒ **通过**；
* 激进配置 +3.6% ⇒ **不通过**（长 K 点积对消放大误差，与之前诊断一致）。

### 为什么 4090 上测不出收益

4090 的 fp32 本来就强（~82 TFLOPS，fp16 165），只差 2 倍；
**V100 的 fp32 只有 15.7，fp16 张量核 125 TFLOPS，差 8 倍** —— 所以 fp16 在 V100 上收益才显著。
⇒ 「fp16 有没有用」**取决于卡**，不能一句话结论。

### 用法（已做成环境变量，不用改代码）

    set TG_FP16=1                 # 打开 fp16 GEMM（默认门槛 K<=1280，推荐）
    set TG_FP16_MAX_K=1000000000  # 更激进：全部 GEMM（实测 41.9ms 但 loss +3.6%，不推荐）
    set TG_FP16_MIN_OUTPUT=0      # 连小 GEMM 也走 fp16

### L3 混合精度判定

| 判据 | 结果 |
| --- | --- |
| 600 步 loss 偏差 ≤2% | **通过（+0.55~0.65%）** |
| 无 NaN | 通过 |

| 覆盖范围 | 仅 V100 验证；4090 上预计收益很小（fp32 本就强），未实测 |

⇒ **L3 混合精度：V100 上通过（默认配置）**；对外表述应写「V100 上 fp16 提速 1.17×、loss 偏差 <1%」。

### 正确但尚未做的（PyTorch 式 AMP）

PyTorch 还能再省两块我们没做：**激活以 fp16 存储**（省显存与带宽）、**loss scaling**。
我们的做法是「只在 GEMM 边界 cast、其余全 fp32」，所以**精度更好但显存不省**。
这一步留作后续（要先有显存压力再讨论，收益不确定）。
### BF16 / INT8 在 V100 上的实测结论（2026-10-30）

**设备事实（实测）**：V100 计算能力 **7.0（Volta）**，`torch.cuda.get_device_name` = Tesla V100-PCIE-32GB。

**BF16 在 V100 上是软件模拟，不是硬件。** 同一形状 4992×256×1280 的 GEMM：

| 精度 | 耗时 | 相对 fp32 |
| --- | --- | --- |
| fp32 | 0.292 ms | 1.00× |
| **fp16** | **0.073 ms** | **4.00× 快**（真张量核） |
| **bf16** | **0.390 ms** | **慢 34%** |

`torch.cuda.is_bf16_supported()` 在 V100 上返回 **True** —— 但那是 **emulation**（PyTorch 2.6 在 sm<80 上把 bf16 降级成 fp32 计算）。
用时延一测就露馅：**bf16 比 fp32 还慢**。

⇒ 结论：
* **V100 上不要用 BF16**（既无速度收益，又只有 8 位尾数，精度还不如 fp16 的 10 位）；
* BF16 要 **Ampere（sm_80+）** 才有硬件支持，4090 可以（等机器回来再测）；
* **INT8**：V100 有 INT8 张量核，但那是**推理量化**的路径；**训练不能用**（梯度是连续量，
  量化误差在长 K 累加后会被放大到不可用，和 fp16 的 1e-2 问题同源但严重得多）。
  正确做法是「训练后量化（PTQ）→ 推理」，属于推理侧工作，不放在训练标准里。

## ★ BF16 已实现并在 A10 上验收（2026-10-30）

### 为什么做 BF16（PyTorch 侧实测，A10 / 25.2M 模型）

| 精度 | ms/step | 末 loss | 速度 | loss 偏差 |
| --- | --- | --- | --- | --- |
| fp32 | 39.8 | 0.045225 | 1.00× | — |
| fp16 | 22.4 | 0.046327 | 1.78× | **+2.44%（超判据）** |
| **bf16** | **22.3** | 0.045282 | **1.79×** | **+0.13%** |

⇒ fp16 的 5 位指数在这里把 loss 拉偏 2.44%，bf16 的 8 位指数只偏 0.13%。
**现代大模型用 BF16 是有道理的**，我们的默认精度也该往这边走。

### 实现（`cuda.py`，由 Grok 4.7 编写，父 agent 验收）

* `CUDA_R_16BF = 14`；两个 NVRTC 内核 `cast_f32_to_bf16`（**RTNE**）/ `cast_bf16_to_f32`；
* `_cast_flat_ptr_bf16`、`_sgemm_bf16`（列主序约定与 `_sgemm` 完全一致，fp32 累加、fp32 输出）；
* 环境开关 **`TG_BF16=1`**（默认关）+ `TG_BF16_MAX_K`（默认 1280）/ `TG_BF16_MIN_OUTPUT`（默认 262144）；
* 在 `_sgemm` 里**先于 fp16** 分发；异常永久回退；**CUDA Graph 捕获期间不启用**（自动走原路径并只提示一次）。

### 验收（A10，全部实测）

| 检查 | 结果 |
| --- | --- |
| `doctor`（不带开关） | **11/11 PASS**（无退化） |
| cast 逐位正确性（10007 元素） | `bits_mismatch = 0` |
| GEMM vs bf16 参考（512³ / 4992×256×1280 / 1280×4992×256） | 4.34e-07 / 2.36e-06 / 6.35e-07 |
| 分发：eligible / 长 K(2000) 回退 / 捕获期回退 | 三条都与对应路径**逐位一致** |
| 单 GEMM 速度 | 4992×256×1280 **1.62×**；1280×4992×256 **1.88×** |
| **整步训练（25.2M，120 步）** | fp32 **36.8 ms / loss 0.044261** → bf16 **30.1 ms / 0.044266** |

⇒ **整步 1.22×，loss 偏差 0.011%。**

### 与 PyTorch 的差距（已知，且有明确修法）

PyTorch autocast 在同样模型上是 **1.79×**，我们是 **1.22×**。
差在**每次 GEMM 都要现 cast A 和 B**（PyTorch 会缓存权重的 bf16 影子副本）。
修法：**给权重做 bf16 影子缓存**（权重一步内不变，按 tensor 身份 + 版本号失效），
预期能把 1.22× 拉到 1.5× 以上。这条留作下一步。
### 尝试过但回退的优化：bf16 影子缓存（2026-10-30）

**动机**：PyTorch autocast 是 1.79×，我们只有 1.22×，差在每次 GEMM 都要现 cast。

**做法**：给 ≥64K 元素的缓冲做 bf16 影子缓存（上限 256 MB），在优化器 `zero_grad()` 时清空。

**结果：收益极小且数值错误，已回退。**

| 配置 | ms/step | 末 loss |
| --- | --- | --- |
| fp32 | 37.0 | 0.044261 |
| bf16（无缓存，提交版） | **30.2** | **0.044265** |
| bf16 + 影子缓存 | 29.8 | **0.044911（偏 1.5%，错）** |

两个原因：

1. **清缓存时机放错了**：训练循环是 `forward → zero_grad → backward → step`，
   `zero_grad` 在 forward **之后**，所以 forward 用的是上一步的旧影子（权重已被 step 更新）。
   正确钩子应该放在 `step()` 末尾，而 `step` 在三个优化器类里各自实现，需要逐处插入。
2. **收益本来就小**：这个模型的激活（1920×512）比权重（512×512）大得多，
   缓存权重只省下约 20% 的 cast 成本。

⇒ 结论：**不带缓存、1.23× 的版本是当前正确的终点**。要再往上，
得先把"按 step 失效"的钩子做对（或者让训练循环显式调用 `rt.bf16_shadow_clear()`），
那是下一轮的事，收益预期 1.3× 左右，不值得为它冒数值风险。
### bf16 长稳（A10，7 分钟 / 21,369 步）+ 修掉量具的一个 bug（2026-10-30）

```
跑了 21369 步 / 7.0 分钟；采样 42 次
loss 首段均值 0.0439 → 末段均值 0.0437
显存峰值 最大 0.283 GiB；增长 0.00%
host RSS 增长 0.00%
NaN/异常 loss 次数：0
RESULT: PASS
```

**先说一个工具 bug（重要，属于"别信量具"那类）**：
`soak_test.py` 原来用 `(max-min)/mean` 判漂移，把**内存下降**也算成漂移。
A10 上 RSS 实际是 0.566 → 0.529（**下降**），却被判成 6.86% FAIL。
已改成只量「增长」：`(末段均值 − 首段均值) / 首段均值`，收缩记 0。
复算后显存 0.00%、RSS 0.00% ⇒ **PASS**。

**结论**：bf16 路径在 A10 上 2.1 万步零漂移、无 NaN、loss 平稳（0.0439→0.0437）。

### A10 上的正面对比（同一模型 25.2M，我们的引擎 vs PyTorch）

| 引擎 | fp32 | bf16 | 自身提速 |
| --- | --- | --- | --- |
| **TGAI GO** | 37.2 ms | 30.2 ms | 1.23× |
| PyTorch（autocast） | 39.8 ms | 22.3 ms | 1.79× |

* **fp32 正面对比：我们快 1.07×**；
* **bf16 正面对比：我们慢 1.35×** —— 差在 PyTorch 缓存了权重的 bf16 影子副本，
  而我们是每次 GEMM 现 cast（这条已知，且我试过加缓存但因钩子时机错误导致数值不对，已回退）。

⇒ 如实记：**bf16 目前只是"我们自己比 fp32 快 1.23×"，正面对比仍落后 PyTorch**。
这是 L3 混合精度下一步要解决的核心问题，不能对外说"bf16 已跟上 PyTorch"。
### bf16 影子缓存：做对了，但收益只有 0.7%（2026-10-30）

**修法**：把失效点从 `zero_grad()`（错，晚半步）改到 **优化器 `step()` 开头**——
那一刻 backward 已经用完本轮影子、下一轮 forward 还没开始，是唯一正确的位置。
缓存在 `_bf16_epoch_bump()` 里整体清空；`AdamW.step` / `Muon.step` 开头各调一次（对 fp32 零影响）。

**结果（A10，25.2M，120 步）**：

| 配置 | ms/step | 末 loss |
| --- | --- | --- |
| fp32 | 37.2 | 0.044261 |
| bf16（无缓存） | 30.2 | 0.044265 |
| **bf16 + 影子缓存（epoch 版）** | **30.0** | **0.044265（与无缓存逐位相同）** |
| `doctor` | — | **11/11 PASS** |

⇒ 数值正确了，但**只快 0.7%**：这个模型里激活（1920×512）比权重（512×512）大得多，
缓存权重只省下约 20% 的 cast 成本。

### 与 PyTorch 的 1.35× 差距是结构性的，不是实现细节

PyTorch autocast 22.3 ms vs 我们 30.0 ms。差别在于：

| | PyTorch AMP | 我们（当前） |
| --- | --- | --- |
| 激活存储 | **bf16**（省一半带宽） | fp32 |
| GEMM 输入 | 直接就是 bf16，**没有 cast 内核** | 每次现 cast |
| 权重 | bf16 影子 + fp32 master | fp32（+ 影子缓存） |

**要真正追上，得做完整 AMP**：激活用 bf16 存储、权重保留 fp32 master、加 loss scaling。
那是一次较大的改动（要改 Tensor 的 dtype 语义），不是调参能解决的。
在做到之前，对外只能说：**bf16 让我们自己比 fp32 快 1.24×，正面对比仍落后 PyTorch 约 1.35×**。
### 自检覆盖 bf16（2026-10-30）

## ★ 多卡数据并行：地基完成，正确性已验证（2026-10-30）

### 做了什么

新增 `python/tgai_go/train/dist.py`（**不依赖 NCCL / MPI / torch.distributed**，自研）：

* `DataParallel.broadcast(params)` —— rank0 的权重分发给所有 rank（保证各卡起点逐位一致）；
* `DataParallel.all_reduce_grads(params)` —— 梯度在本机**共享内存**里做全归约并求平均；
* `world=1` 时以上全是**快速空操作**（单卡行为零变化）；
* 训练脚本通过 `T.DataParallel` 接入（torch 孪生那边 `T` 上没有这个属性，自动降级，孪生代码仍只差 import）。

新增 `tools/launch_dp.py` —— 每个 rank 一个进程、各绑一张卡（`CUDA_VISIBLE_DEVICES`），
并设置 `TGAI_DP_WORLD/RANK/JOB`。

### 验证（今天能做的部分，全部实测）

| 检查 | 结果 |
| --- | --- |
| **2 进程（CPU）broadcast + 全归约正确性** | `tools/test_dp.py` → **PASS**（两个 rank 都拿到 rank0 的权重；梯度等于各 rank 算术平均） |
| **world=1 是否零影响**（V100，600 步） | **53.3 ms/step、loss 0.088585** —— 与基线（53.0 / 0.0885x）一致 |
| 启动器冒烟 | `launch_dp.py --world 1` → PASS，环境变量正确注入 |
| 孪生一致性 | `make_twins.py --check` **一致** |

### 过程中修掉的一个死锁（值得记）

第一版 barrier 是「各 rank 落一个文件、到齐即通过」，但 **rank0 通过后立刻删掉自己的标记**，
rank1 可能还没看到就已经被删掉 ⇒ **2 进程永久等待**（实测超时 120 秒）。
改法：barrier 加**自增世代号**、标记文件**不删除**，`close()` 时统一清理。

按 L1 判据「速度 ≥ PyTorch 0.9×」：**A10 的 fp32 不达标（0.88×）**，bf16 勉强达标（0.93×）。

### 排查过程（两个假设，一个被否）

**假设 1：Python 侧启动开销**（348 次/步 × 8 µs ≈ 2.8 ms）
→ 开 CUDA Graph 实测 **64.4 → 64.1 ms（只省 0.5%）** ⇒ **假设不成立**。

**假设 2：内存带宽**（A10 = 600 GB/s，V100 = 900 GB/s；A10 fp32 算力却比 V100 高一倍）
分层计时支持这个解释：

| 阶段 | A10（10M） | V100（同配置） |
| --- | --- | --- |
| forward | 22.15 ms | 17.41 ms |
| backward | **41.12 ms** | 34.28 ms |
| cross_entropy | 0.84 ms | 0.70 ms |
| optimizer | 1.08 ms | 1.13 ms |
| **合计** | **65.19 ms** | 53.0 ms |

我们的每步有 348 个小内核（`adamw_update` 74、`permute8` 64、`ewise_add_v4` 57…），
**绝大多数是内存受限**。算力翻倍但带宽只有 V100 的 2/3，于是"算得快、搬得慢"，反而更慢。
PyTorch 的算子更少更粗（900 次启动但每次搬运更整块），在低带宽卡上更占便宜。

* **不是"引擎变差了"**，是"我们的形状在这类卡上不占优"；
* 要改善 A10 这类卡，方向是**减少搬运**（融合更多 elementwise、把 permute 消掉），

* 这条**不影响** 4090 / V100 的结论，但必须写进标准：**"快过 PyTorch" 有硬件前提**。

## ★★ softmax 重写：A10 从 0.88× 拉回到 1.00×（2026-10-30）

### 怎么找到的（不猜，先量）

给 `tools/profile_step.py` 加了 **`--gpu`**：每次 kernel 前后各记一个 CUDA event，
结束后统一 sync 汇总，得到**按 kernel 的 GPU 时间**（之前只有 host 启动时间，找不到真凶）。

A10 上第一步结果（fp32，10M，B=78，S=64，每步 65 ms）：

| kernel | 次数/步 | GPU ms/步 |
| --- | --- | --- |
| **softmax_lastdim_bwd** | 8 | **8.74** |
| **softmax_lastdim** | 8 | **5.31** |
| emb_bwd_owned | 2 | 2.95 |
| permute8 | 64 | 2.43 |
| silu_mul_bwd | 8 | 2.10 |
| **我们的 kernel 合计** | 348 | **32.40** |

**softmax 前后向 14.05 ms = 整步 21%**，比任何 GEMM 都大；而它只搬 ~82 MB
（按 600 GB/s 应 ≈0.14 ms）⇒ **慢了近 100 倍**，是写法问题。

### 根因

```cuda
// 旧版：一行一个线程，内部串行跑 3 遍 k
int r = blockIdx.x * blockDim.x + threadIdx.x;
for (int j = 1; j < k; ++j) m = fmaxf(m, row[j]);     // 串行
for (int j = 0; j < k; ++j) { e = expf(...); sum += e; }
for (int j = 0; j < k; ++j) orow[j] *= inv;
```

624 行 = **只有 624 个线程**在干活（A10 有 6144 个 CUDA 核），且无向量化、无合并访存。

### 改法：一行一个 warp

32 个 lane 覆盖连续的 `j`（天然合并访存），`__shfl_xor_sync` 做 max/sum 归约；
host 侧 grid 改为 `ceil(rows/8)`、block 固定 256（8 warp）。反向同理。

### 结果

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| **我们的 kernel GPU 合计** | 32.40 ms | **20.07 ms（−38%）** |
| softmax 是否还在前 6 | 第 1、2 名 | **已掉出前 6** |
| A10 fp32 整步 | 64.4 ms | **57.0 ms**（3 次：57.7/57.0/54.7） |
| A10 bf16 整步 | 54.8 ms | **52.9 ms**（2 次：54.1/51.6） |
| `doctor` | — | **12/12 PASS** |

（各测多次取中位，同一台机器、同一份语料）

## ★★ 词嵌入反向：阈值 1024 → 8192（A10/V100 双赢，2026-10-30）

### 怎么发现

GPU 归因（`--gpu`）里 `emb_bwd_owned` **只有 2 次调用却吃 2.98 ms/步**，是 softmax 之后的最大单点。

### 根因

```cuda
// 独占版：每个 block 扫【全部 seq】，只处理 id % blocks == mine 的 token
for (int t = 0; t < seq; ++t) {
    int id = ids[t];
    if (id < 0 || id >= vocab || (id % blocks) != mine) continue;
    ...
}
```

我们的形状（seq=4992、vocab=360）下：256 个 block × 4992 次扫描 = 128 万次迭代，
其中只有 4992 次真正干活 ⇒ **99.7% 是空转**。
而 `seq < 1024` 才会走原子版，所以我们 4992 一直走的是这条慢路。

### 改法

把阈值抬到 **8192**：常规序列一律走原子版；独占版只留给原注释针对的「超长序列 + 小词表」场景。
（没删那条路径 —— 它在 8192 场景下是别人实测选的，我不拿一次实验推翻它。）

### 结果

| 指标 | 前 | 后 |
| --- | --- | --- |
| **A10：我们 kernel 的 GPU 合计** | 20.07 ms | **15.77 ms（−21%）** |
| **V100：整步 600 步** | 53.3 ms | **46.0 ms（2 次：46.0/45.9，−13.7%）** |
| A10：整步 | 57.0 ms | 55.8 ms（单次，落在原波动范围内，不宜单独引用） |
| `doctor`（A10 / V100） | — | **12/12 / 12/12 PASS** |
| 600 步 loss（V100） | 0.08854 | **0.088567 / 0.088542** |

**V100 上 fp32 现在是 46.0 ms vs PyTorch 52.4 ms ⇒ 快 1.14×**（此前是 53.0 ms、约 1.00×）。

> 原子版让求和顺序不固定，loss 有 ±0.05% 的抖动（0.088542~0.088567），
> 比 fp32 的 run-to-run 噪声（±0.08%）还小，可接受；但**意味着不可逐位复现**，要写进文档。

## ★★ permute 向量化：A10 49.3 ms / V100 41.4 ms（2026-10-30）

### 根因

`permute8` 是 8 维通用 gather，**每个元素跑 8 次整数除法+取模**（每次约 20 周期）。
我们每步要搬 64 次 permute × 1.28M 元素 ≈ 8200 万个元素 ⇒ 完全是算索引算死的，不是带宽。

### 改法

加 `permute8_v4`：最内层维在源和目的都连续（stride==1）且能被 4 整除时（我们的
`(B,S,NH,DH)↔(B,NH,S,DH)` 正好满足，DH=32），按 **float4** 一组处理——
索引计算量降到 1/4、线程数降到 1/4。不满足条件时仍走通用 `permute8`。

### 结果

| 指标 | 前 | 后 |
| --- | --- | --- |
| **permute 的 GPU 时间（A10）** | 2.55 ms | **1.44 ms（−44%）** |

## 段错误排查结论（2026-10-30，第 27 轮）

### 现象与量化

上传 `cuda.py` 后**第一次**运行偶发段错误（两次），复跑即正常。为量化，在 A10 上连跑
6 次完整「导入 + NVRTC 编译 + 自检」：

```
run1 rc=0  run2 rc=0  run3 rc=0  run4 rc=0  run5 rc=0  run6 rc=0
崩溃次数 0 / 6
```

⇒ **不可复现**。所以不能据此说"引擎不稳"，但也**不能当它没发生**。

### 两次崩溃的共同点 → 最可能的解释

两次都发生在**刚上传完 `cuda.py` 的第一次运行**。上传工具是**直接覆盖目标文件**的，
如果另一端在文件写到一半时执行 Python，就可能导入到「参数表是新的、内核源码是旧的」
（或反之）的混合状态 —— 而 `cuLaunchKernel` 按错误的参数表传参会**越界写**，表现为段错误
（而不是 Python 异常）。

### 已做的加固

`tools/ms_agent.py` 的 PUT 改为**原子写**：先写 `<path>.part` → `fsync` → `os.replace`。
rename 在同一文件系统内是原子的，另一端要么看到旧文件、要么看到完整新文件，不可能看到半截。

⚠️ **需要在 notebook 里重启一次 agent 才生效**（我这边重启会中断自己的通道）：

```bash

cd /mnt/workspace && MS_TOKEN=TGAI_9f3x nohup python3 ms_agent.py > agent.log 2>&1 &
```

重启后隧道地址不变（pinggy 只转发 TCP，8080 上重新监听即可）。

### 下次复现时该做什么（写下来，不再"复跑一次就过"）

1. 先比对 md5：本地 `cuda.py` vs 远端，不一致 ⇒ 就是半截文件；
2. 若 md5 一致仍崩，抓 `faulthandler`（`python3 -X faulthandler`）+ `CUDA_LAUNCH_BLOCKING=1` 定位到具体 launch；
3. 仍无法定位就上 `cuda-gdb` 抓 GPU 侧栈。

### ★ 反直觉发现：优化之后，bf16 在 A10 上不再更快

| 时点 | fp32 | bf16 | bf16 收益 |
| --- | --- | --- | --- |
| 今天早些时候（三个 kernel 优化前） | 64.4 ms | 54.8 ms | **1.18×** |
| 优化后（现在） | 48.8 ms | 49.5 ms | **0.98×（略慢）** |

原因很清楚：bf16 只加速 **GEMM**，但每步要多发 **147 个 cast 内核**（495 vs 348 次启动）。
以前非 GEMM 部分（softmax/emb/permute）吃掉了大半个步，GEMM 占比高，bf16 划算；
把这些 kernel 修好之后，**GEMM 的占比下降、cast 的固定成本占比上升**，两者刚好抵消。

**结论（要写进文档）**：bf16 是否值得开，取决于「这一步里 GEMM 占多少」，
不能一句"bf16 更快"了事。对 10M 模型 + 优化后的引擎，A10 上 **建议不开**；
模型更大（GEMM 占比更高）时再开。`doctor`/`accept.py` 的 bf16 项判据是"不慢于 fp32 5%"，
所以这里判 PASS 是**正确**的 —— 它没说"必须更快"。

## checkpoint 存/续：补上并验证（2026-10-30，第 30 轮）

### 先承认一个过度声明

L1 判据里有一行「checkpoint 存/续：中断后从最近 step 恢复，loss 曲线不跳变」，
而我之前一直把 L1 报成 **4/4 全部通过** —— 实际上训练脚本**根本没有 `--resume`**，
这条从来没验证过。已补上，并把状态改成"部分验证"。

### 实现

* `--save-resume X.npz`：训练结束后把权重（+step）存成 npz（**与部署用的 .TG 分开**，互不影响）；
* `--resume X.npz`：开机时原地覆盖权重再训练。

### 验证（V100）

| 运行 | 步数 | **第 41 步 loss** | 末步 loss |
| --- | --- | --- | --- |
| A：连续跑 80 步 | 80 | **0.337546** | 0.095957 |
| B：跑 40 步 → 存档 → 续训 40 步 | 40+40 | **0.337557** | 0.108924 |

断点处差 **0.003%**（3e-5 量级）⇒ **loss 曲线不跳变** ✅

### 已知局限（必须写清，不能藏着）

**优化器状态（Adam 一阶/二阶矩）没有存**，所以续训后动量从零重来：
A 末步 0.095957 vs B 末步 0.108924 = **差 13.5%**。
这在"训练中途崩了要接着跑"的场景里是可以接受的（模型没坏、方向没丢），
但**不等于无损续训**。下一步要么把 Adam 状态一起存，要么明确接受这个代价。

### 踩到的坑

续训后第一次 `backward` 报「调用 backward 的张量不参与求导」——
因为用 `T.tensor(arr)` 新建张量替换 `p[k]`，新张量默认**不是可导叶子**。
改成**原地覆盖** `p[k].data[...] = arr`（保留原张量的 requires_grad 与身份）后才正确。
### 续训再进一步：偏置修正已恢复（2026-10-30，第 31 轮）

在存档里追加优化器状态（防御式：取不到就跳过并明确告知）。

**V100 实测（40 步 → 存档 → 续训 40 步）**：

| | 首步 loss | 末步 loss | 与连续 80 步的差 |
| --- | --- | --- | --- |
| 连续 80 步 | — | **0.095957** | 基准 |
| 续训（上一版，只存权重） | 0.337557 | 0.108924 | **+13.5%** |
| **续训（本版）** | **0.337451** | **0.099056** | **+3.2%** |

* 断点处差 **3e-5 ⇒ 无跳变** ✅
* 末 loss 差从 **+13.5% 降到 +3.2%** —— 因为 **Adam 的 step 计数（偏置修正）被恢复**了；
* **一阶/二阶矩（m/v）仍未取到**：打印明确显示「优化器状态恢复 0 个张量（存档里没有）」，
  说明我们的 `AdamW` 内部属性名不是 `m`/`v`。**下一步只需查清真实属性名即可补全。**

> 这一版是**加了能力、没弄坏任何东西**（取不到时行为与上一版完全一致，并有明确提示），
> 但 **m/v 恢复这条尚未验证成功**，所以不能算"无损续训"。
#### 更正：卡点不是属性名，是 GpuBuf 缺少设备端写入接口

上一轮我写"AdamW 内部属性名不是 m/v"，**这个判断错了**。查代码后确认：

```python
class AdamW(_Optim):
    def __init__(...):
        self.m = []          # ← 名字就是 m
        self.v = []          # ← 名字就是 v
        for p in self.params:
            if cuda: self.m.append(rt.zeros(...))   # 设备上的 GpuBuf
```

**真正的原因**：`self.m[i]` 是 `GpuBuf`（设备缓冲），而 `GpuBuf` 目前只有
`__init__ / __del__ / to_numpy()` —— **没有任何"把主机数组写回设备"的方法**，
所以我代码里 `_t.data[...] = arr` 抛异常被 try 吞掉，恢复数为 0。

⇒ 下一步很明确（也很小）：给 `GpuBuf` 加一个 `copy_from(numpy_array)`（内部 `cuMemcpyHtoD`
+ 必要时 sync），然后用它恢复 `m`/`v`。这是**一个方法 + 一行调用**的活，
不需要再动训练逻辑。

> 记这一笔是为了防止下次照着"属性名不对"这条错线索白跑一趟 ——
> **文档里的错误结论比没有结论更危险。**
### ★ 无损续训达成（2026-10-30，第 33 轮）

**关键发现**：`opt.m[i]` / `opt.v[i]` 是 **GpuBuf**（设备缓冲），没有 `.data` 可原地写；
但运行时已有 `rt.h2d(arr)` —— 直接用它在载入时**建新缓冲替换**列表项即可，不必给 GpuBuf 加方法。

**V100 实测（40 步 → 存档 → 续训 40 步，同一份语料/种子）**：

| 版本 | 断点首步 loss | 末步 loss | 与连续 80 步的差 |
| --- | --- | --- | --- |
| 基准：连续 80 步 | — | **0.095957** | — |
| 只存权重 | 0.337557 | 0.108924 | +13.5% |
| + 恢复 `opt.t`（偏置修正） | 0.337451 | 0.099056 | +3.2% |
| **+ 恢复 m/v（本版）** | **0.337417** | **0.096017** | **+0.06%** |

⇒ **续训现在基本无损**（0.06% 属于浮点累加顺序的正常差异），断点处无跳变（3e-5）。

**L1 的 checkpoint 判据至此真正通过**（此前是"无跳变但末 loss 差 13.5%"）。
实现要点：`--save-resume X.npz` 存权重 + step + Adam 的 m/v + t；`--resume X.npz` 全部还原。
权重用**原地覆盖**（保 requires_grad），矩用 **`rt.h2d` 建新 GpuBuf 替换**。
