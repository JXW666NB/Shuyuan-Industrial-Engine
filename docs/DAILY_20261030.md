## 三、今天修掉的真 BUG（都不是"优化"，是会让用户崩的）

1. **`bmm` 在 Python 里按 batch 循环**调 cuBLAS（注意力每层 624 次调用）→ 换 strided batched，注意力块 **17.9×**
2. **池裁剪崩溃**：launch 快路径把释放记录改成裸指针，裁剪函数仍按元组解包 ⇒ 语料一大就 `TypeError`
3. **`reshape(-1, D)` 不支持负维度** —— PyTorch 用户最常用写法
4. **`TG_CORPUS` 是追加不是替换** ⇒ 语料悄悄翻倍（我一度误判为"代码退化 1.84×"）
5. **语料解析失败静默回退到 5 条内置样例** ⇒ 用户可能"训了三天发现训的是示例数据"
6. **整个语料当一个 batch** ⇒ 2M 字符就在 49 GB 的 4090 上 OOM（那个 6 万字上限一直在掩盖它）

## 四、方法论上的三条教训

1. **微基准必须 `sync()`** —— 不加同步测出"单次 GEMM 0.03 ms"，差点把优化方向带偏。
2. **不要拿历史基线比** —— 这台机换了实例/被产线占卡后，同形状 PyTorch 自身就慢 45%；
   一切对照必须**同会话**。同理，我给 TGAI 做的优化也**同时提速了 PyTorch 基线**（one-hot → embedding），
   所以"追平"一度是拿旧基线算出来的假象，后来才纠正为 1.26× 慢。
3. **判据先验证再采信** —— 子智能体报的"loss 偏差是混沌"，我做了梯度对拍才发现是梯度真错了 2%。
