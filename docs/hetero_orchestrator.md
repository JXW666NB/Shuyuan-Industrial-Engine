# TGAI GO 训练化 · 异构资源调度设计

> 版本 v0.1 / 2026-10-27
> 作者：DeepSeek（规划），算子实现：Grok 4.7 / DeepSeek-Flash（已交付 7 个反向 kernel，7/7 对拍通过）
> 原则：**先量后做**。文中所有数字要么来自实测，要么给出假设，不写"预计会很快"这种话。

---

## 0. 一句话结论

> **异构多卡的关键不是算力总和，而是"把对的算子放到对的卡上"。**
> 把 AMD/国产卡当"显存仓库"是亏的（两跳 PCIe，比内存还慢）；
> 让它**参与计算**（跑 memory-bound 的优化器更新、归一化、elementwise）才赚。

## 1. 显存账（2.97B 参数，实测维度 28 层/d=1024/ff=4096/E=8/vocab=32779）

| 状态 | 精度 | 大小 | 说明 |
|---|---|---|---|
| 权重 | fp16 | **5.5 GB** | 前向+反向都要读 |
| 梯度 | fp16 | **5.5 GB** | 反向产出 |
| fp32 主权重 | fp32 | **11.1 GB** | 混合精度必需（V100 无 bf16） |
| **Muon 动量** | fp32 | **11.1 GB** | 只存一阶矩（2D 矩阵，占 99% 参数） |
| AdamW m+v | fp32 | **~0.3 GB** | 只给 1D/norm/embedding/router |
| **小计（不含激活）** | | **33.5 GB** | |

对比：如果全用 AdamW，光 m+v 就要 22.1 GB，小计 **44.3 GB**。
**Muon 把优化器状态砍掉一半，这是它在这个项目里最实在的价值。**

### 1.1 各容量单卡怎么放

| 卡容量 | 常驻显存 | 放主机内存 | 剩余给激活 | 判定 |
|---|---|---|---|---|
| **16 GB**（2×V100-16G 的单卡） | 权重+梯度 11.0 | 主权重 11.1 + 动量 11.1 | **~4.5 GB** | ⚠️ 能跑，micro-batch 很小 |
| **22 GB**（2080 魔改） | 权重+梯度+动量 22.1 | 主权重 11.1 | **~0 GB** | ❌ 装不下，必须再分片 |
| **32 GB**（V100-32G） | 权重+梯度+动量 22.1 | 主权重 11.1 | **~9.9 GB** | ✅ 推荐配置 |
| **48 GB**（4090 魔改） | 全部 33.5 | — | **~14.5 GB** | ✅ 最舒服 |

> 注意：22 GB 是个尴尬位置 —— 比 16 GB 多不了多少，却比 32 GB 少 10 GB。
> 2080 这类卡的正确用法是**配合大卡做异构**，不是单独训 3B。

## 2. 「NVIDIA 算、AMD 存」划算吗

同一份优化器状态（11.1 GB 动量），三种放法每步的搬运代价：

| 放置 | 跳数 | 有效带宽 | 每步搬运 | 耗时 |
|---|---|---|---|---|
| **主机内存**（DDR4 + pinned） | 1（GPU↔RAM） | 6–8 GB/s | 11.1 下行 + 5.5 上行 = 16.6 GB | **~2.1–2.8 s** |
| **第二张 GPU 当仓库** | **2**（GPU→RAM→GPU） | 3–4 GB/s | 16.6 GB | **~4.2–5.5 s** ❌ |
| **留在本卡**（32 GB 卡） | 0 | — | 0 | **0** ✅ |

**结论**：
1. 「GPU 当显存仓库」**全面劣于主机内存**（两跳 + 更贵），没有工程价值。
2. 第二张卡的唯一正确用法是**参与计算**：把 memory-bound 的算子（优化器更新、rmsnorm、silu、残差、梯度裁剪）放过去，让 CUDA 卡专注 GEMM。
3. 只有当第二张卡与第一张**同 NVLink 域**时，"当仓库"才可能不亏 —— 而 V100 PCIe 没有 NVLink。

## 3. 多卡方案

### 3.1 同构多卡（2/4/8 张同型号）

| 卡数 | 方案 | 每卡常驻 | 每步梯度规约 | 规约耗时（6–8 GB/s） |
|---|---|---|---|---|
| 2×32G | ZeRO-1（只分片优化器） | 11.0 + 5.55 + 5.55 ≈ 22.1 | 5.5 GB | 0.7–0.9 s |
| **2×16G** | **ZeRO-2（梯度+优化器分片）** | 11.0 + 2.75 + 5.55 ≈ 19.3 ❌ | 5.5 GB | 0.7–0.9 s |
| 4×16G | ZeRO-2 + 主权重分片 | 11.0 + 1.4 + 2.8 + 2.8 ≈ 18.0 ❌ | 5.5 GB | 0.7–0.9 s |
| 8×16G | ZeRO-3（权重也分片） | 1.4 + 0.7 + 1.4 ≈ 3.5 ✅ | 5.5 GB | 0.7–0.9 s |

**2×16G 的现实**：即使 ZeRO-2，每卡仍需 ~19 GB > 16 GB ⇒ **必须叠加 CPU offload**（主权重+动量放内存），
此时每卡常驻 11.0 + 2.75 ≈ 13.8 GB，剩 2 GB 激活 —— micro-batch 只能 ~512 tokens。
**这就是国内 2×16G 服务器的真实困境，不是软件能变魔术解决的。**

### 3.2 同厂异构（2080-22G + V100-32G）

| 卡 | fp16 算力 | 显存 | 相对 V100 |
|---|---|---|---|
| V100-32G (sm_70) | ~112 TFLOPS | 32 GB | 1.0× |
| 2080-22G (sm_75) | ~13 TFLOPS | 22 GB | **0.12×** |

**朴素数据并行的效率**（等最慢卡）：
`2 × min / (sum) = 2 × 13 / 125 = 20.8%` —— 比单用 V100 还慢。

**可行方案：按算子类型分工（不是按数据分工）**

| 算子类型 | 放哪 | 理由 |
|---|---|---|
| attention / MoE GEMM（算力密集） | **V100** | 快 8.6× |
| optimizer 更新、rmsnorm、silu、残差、梯度裁剪（访存密集） | **2080** | 这些算子受带宽限制，2080 的 448 GB/s 与 V100 的 900 GB/s 差距远小于算力差距 |
| 数据预处理/分词 | CPU | — |

按这个分工，2080 承担约 15–25% 的**时间**，V100 承担剩余 → 有效效率可达 **60–75%**
（对比朴素并行的 21%）。**这是异构真正的价值点。**

### 3.3 跨厂（AMD + NVIDIA 同机）

**诚实结论：CUDA + HIP 直接互操作不可行。**

| 障碍 | 说明 |
|---|---|
| 两个 runtime | 同进程加载 CUDA + HIP 极不稳定；主流做法是两进程 + 自定义通信 |
| 无 P2P | cudaMemcpyPeer 不认 HIP 设备；只能主机中转（两跳） |
| 无统一地址空间 | 无法共享张量，只能序列化搬运 |
| Windows 无 ROCm | 目标机是 Windows，AMD 侧只剩 Vulkan / DirectML |

**唯一现实路径：Vulkan Compute 后端 + 主机中转**

| 项 | 估计 |
|---|---|
| Vulkan GEMM 效率（手写 shader） | 约为 cuBLAS 的 **50–70%** |
| 主机中转带宽 | 3–4 GB/s（两跳） |
| 可行的分工 | NVIDIA 跑 GEMM；AMD/国产卡跑 optimizer + elementwise（数据量小、算力要求低） |
| 效率上限 | 相对单 NVIDIA 卡 **< 1.3×**，且仅在小模型/大显存场景成立 |

**什么时候值得做**：国产卡显存巨大（32–64 GB）且便宜，用来做"优化器宿主 + elementwise 计算"确实能省下主机内存与 CUDA 卡显存。
**什么时候不值得**：想靠它获得比 NVIDIA 更高的吞吐 —— 不可能。

> 真正的"国产卡可用"入口是 **Vulkan**（摩尔线程等对 Vulkan 支持良好），
> 而不是把 CUDA 代码翻译成国产 runtime。

## 4. 通信压缩层（1-bit SGD + 误差反馈）

这是让"低带宽设备也能参与"的唯一手段，也是异构/多卡的核心优化。

```
每步：
  1. 本地算梯度 g
  2. r += g                     # 残差缓冲
  3. q = sign(r)                # 1 bit/参数
  4. 上传 q（压缩 32×）
  5. all-reduce 后得到全局符号 S
  6. r -= |S| * S               # 误差反馈：把量化误差留在本地
  7. 用 S * scale 更新
```

| 场景 | 压缩前 | 压缩后（32×） |
|---|---|---|
| 2×16G 梯度规约 | 5.5 GB → 0.7–0.9 s | 0.17 GB → **25–30 ms** |
| 32×ESP32 集群 | 6 MB → 0.55 s | 0.19 MB → **17 ms** |
| 跨厂主机中转 | 16.6 GB/步 → 4–5 s | 0.52 GB → **0.15 s** |

**分层压缩策略**（避免精度崩）：
- 专家矩阵（99% 参数）：1-bit + 误差反馈
- attention 投影：8-bit
- embedding / router / norm：**不压缩**（它们对精度最敏感，且参数量小）

## 5. MCU 集群算例（32× ESP32-P4）

| 项 | 数值 |
|---|---|
| 单卡算力 | ~0.5–1 GFLOPS（估） |
| 32 卡总算力 | 16–32 GFLOPS（= V100 的 **0.03%**） |
| 总显存 | 32 × 16 MB = 512 MB |
| 链路 | 100M 以太网 ≈ 11 MB/s |

**目标模型**：1.5M 参数（d=128、2 层、vocab 8k、ff=512）

| 指标 | 估算 |
|---|---|
| 每步 FLOPs（2048 tokens） | 18 GFLOP |
| 计算（10 GFLOPS 有效） | ~1.8 s |
| 梯度规约（6 MB） | 0.55 s（压缩后 17 ms） |
| **合计** | **~2.4 s/步**（压缩后 ~1.85 s） |
| 100M tokens 训练 | 4.9 万步 ≈ **33 小时** |

**结论**：这是**有科学意义的极端测试床**，不是纯炫技 ——
它逼你把「梯度压缩 + 传输抽象 + 低带宽同步」做到极致，而这些对 GPU 异构集群同样必要。

## 6. 纯 C 框架模块划分

```
tgai_train/
├── core/        tensor（连续 fp32/fp16 缓冲、strides、设备标签）
├── backend/     cuda.cu / vulkan.cpp / cpu.c  统一接口：alloc/copy/launch/event
├── ops/         前向（复用 TGAI GO）+ 反向（已交 7 个）+ GEMM（cuBLAS）
├── optim/       muon.c（NS 迭代 + 动量）/ adamw.c（1D 参数）
├── comm/        allreduce（环形）/ compress（1-bit + 误差反馈）/ transport（TCP/Vulkan/自定义）
├── sched/       cost_model.c + placement.c（静态放置 + 运行期回退）
├── data/        分词、packing、异步预取
├── ckpt/        分片 checkpoint / 恢复
└── cli/         train / eval / resume
```

**与产线解耦**：训练侧**不链接** `libtgai_engine_gpu.dll` 的导出符号，而是：
- 复用 `cuda/tgai_cuda.cu` 的**源码**（复制到 `ops/`），编译成独立的 `libtgai_train_cuda.dll`
- 产线 DLL 与模型文件**零改动**
- 反向 kernel 通过 NVRTC 运行期编译，避免再次踩 nvcc/MSVC 的坑

## 7. 验证分级（每级都要有判据）

| 级别 | 内容 | 判据 |
|---|---|---|
| L0 | 单算子反向 | 与 PyTorch 逐元素误差 < 2e-4 ✅ **已完成（7/7）** |
| L1 | 单层（attention + MoE FFN）前向+反向 | 梯度相对误差 < 1e-3 |
| L2 | 单步（完整模型一次 fwd+bwd+Muon 更新） | 与 PyTorch 同配置参数更新后权重误差 < 1e-4 |
| L3 | 100 步 loss 曲线 | 与 PyTorch 曲线偏差 < 2%（同一 seed、同一数据） |
| L4 | 多卡（2 卡） | L3 判据 + 单卡/双卡 loss 一致 |
| L5 | 异构（2080+V100） | L4 判据 + 效率 ≥ 60% |

## 8. 风险清单

| # | 风险 | 后果 | 检测手段 |
|---|---|---|---|
| 1 | 反向算子静默错误 | loss 先降后崩 | L0–L3 分级对拍，每级必过 |
| 2 | 1-bit 压缩导致收敛变差 | 训练不动 | 先只在专家矩阵上开，对比 8-bit/无压缩曲线 |
| 3 | Muon 在 MoE 上开销失控（每专家一次 NS） | 反比 AdamW 慢 | 实测 NS 占比，必要时对小矩阵退回 AdamW |
| 4 | V100 fp16 溢出 | 出现 NaN | loss scaling + 梯度裁剪 |
| 5 | 异构调度误判 | 比单卡更慢 | 代价模型先离线校准，再开运行期回退 |
| 6 | Vulkan 后端 GEMM 效率过低 | 跨厂方案无意义 | 先做单 GEMM 基准，低于 cuBLAS 50% 就砍 |

## 10. 最该砍掉什么

**Vulkan 跨厂训练**（P5）和 **MCU 集群**（P6）都应该**放在最后、且随时可砍**。
它们的价值在叙事与极端测试，不在吞吐。

真正能落地的三件事，按优先级：
1. **单卡 32G + Muon + CPU offload 训 2.97B**（P2）
2. **2×16G 的 ZeRO-2 + 1-bit 压缩**（P3）—— 这是国内存量服务器的主场景
3. **同厂异构按算子分工**（P4）—— 这是"老卡农场"的真需求
