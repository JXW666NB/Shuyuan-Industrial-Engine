# 为什么用 TGAI GO

> 本文所有数字都来自本仓库的实测记录（`docs/speed_optimization_brief.md`、
> `training/ACCEPTANCE_TRAIN_CUDA.md`、桌面 `TGAI GO测试报告/`），没有估算值。

## 一句话

**TGAI GO 现在的价值是「训练完直接上产线、部署极轻」，不是「训练更快」。**
训练速度到这一轮为止刚好追平 PyTorch（1.02–1.05×），还没反超 —— 想反超要做整层融合（见 §5）。

---

## 1. 部署侧：这是真正能说服人的地方

| 维度 | TGAI GO | PyTorch | 依据 |
|---|---|---|---|
| 运行时依赖 | **C 引擎 + `.TG` 单文件，零 Python 依赖** | 需要整套 Python + torch（约 2 GB 环境） | 产线 `D:\TGAI\libtgai_engine_gpu.dll` 直接加载 `.TG` |
| 权重格式 | `.TG` 一个文件（自描述头 + 权重 + 词表 + 对话模板） | `.pt`/`.safetensors` + 额外代码定义结构 | `chat10m.TG` 40.4 MB，引擎 `generate()` 直接可用 |
| 训练→部署 | **同一份权重直接进引擎，不需要转换脚本** | 通常要导出 GGUF/ONNX 或重写前向 | 两个考试都是训完立刻用引擎跑通 |
| 长上下文推理 | seq=8192 吞吐 **56.7k tok/s**（0.144 s/step） | 对照见 `docs/goal_final_report.md` A 段 | A2/A3 实测 |
| 显存 | MoE 基准峰值 **3.418 GiB** | 2.966 GiB（同精度） | A3 实测，TGAI 低 15% |
| 对话模板 | 写在 `.TG` 里（v27 九标记），引擎自动套 | 需自己拼 prompt | `write_chat_meta.py --preset v27` |

**适用场景**：边缘/离线部署、不能装 Python 环境的地方、"一个文件就是模型"的分发、
需要自己掌控推理内核（改 kernel、加算子）的场景。

## 2. 训练侧：4090 上已快 1.25×，V100 上仍慢 1.12×

10M 对话模型（B=78, S=64, D=256, NH=8, L=8, FF=1280），600 步实测：

| 机器 | TGAI GO | PyTorch | 比值 |
|---|---|---|---|
| **RTX 4090（torch 2.2.2）** | **21.7 ms/step** | **27.1 ms/step** | **快 1.25×**（我们赢在融合 RMSNorm 不受 torch 版本限制） |
| V100（torch 2.6） | 58.7 ms/step | 52.4 ms/step | 慢 1.12×（两边都有融合 RMSNorm，同条件） |
| 4090 两边强制组合式 RMSNorm | 27.6 ms/step | 26.4 ms/step | 慢 1.05×（拉平 RMSNorm 能力后的真实差距） |

**这是从 19.3× 慢追回来的**，四轮优化过程与证据见 `speed_optimization_brief.md`：

| 轮次 | 修什么 | 单项收益 |
|---|---|---|
| ① | `bmm` 从 Python 按 batch 循环 → `cublasSgemmStridedBatched` | 注意力块 17.9×，整步 605→65 ms |
| ② | 带 `ignore_index` 的 CE 从"拷 CPU" → GPU 选择矩阵 | CE 15×，整步 66.5→53.3 ms |
| ③ | 手写 RMSNorm → 后端融合 `nn.RMSNorm` | 每次 3.6×，整步 53.3→40.7 ms |
| ④ | 手写 SiLU-GLU → 后端融合 `silu_mul` | 整步 40.7→33.0 ms |

每次改动都跑了回归，数值与修前**逐位一致**（llama 4.261e-07 / qwen2 4.403e-06 / gpt2 1.857e-07、
conformance 13/13 双后端、pipeline 5.3091→0.1755）。

## 3. 为什么"追平"值得说

这个引擎原本只有推理，训练是纯 Python 逐算子。四轮改的都是**真实工程缺陷**：

- 一个 `bmm` 的 batch 循环（624 次 ctypes 调用）吃掉了 9.3 倍性能；
- 一个 `ignore_index` 分支把 7 MB 张量拷到 CPU，吃掉 13%；
- 手写 RMSNorm 用 6 个算子代替 1 个融合核，吃掉 25%。

**这些缺陷在别的自研框架里同样常见**，修法可复用。

## 4. 不适用 / 老实说的短板

| 短板 | 现状 |
|---|---|
| **多轮对话** | 未达。多轮训练试了两版都退化成复读（字符级小模型只学回答会塌），当前只支持单轮 |
| **模型能力** | 10M 字符级 + 78 条语料，只能"在域内说人话"，不是通用助手 |
| **通用性** | 融合核只覆盖手写模型用到的形状（D=256/NH=8/FF=1280），不追求通用 |
| **生态** | 没有 PyTorch 的算子库、分布式、混合精度、调试工具链 |
| **训练速度** | 追平但没反超；要反超需要整层融合 |

## 4.5 训练速度的真实天花板（已实测，重要）

一步 10M 模型的计算量 `6·P·T = 301 GFLOP`。V100-32GB 的 **fp32** 峰值是 7.8 TFLOP/s：

| | 耗时 | 有效算力 | 占 fp32 峰值 |
|---|---|---|---|
| TGAI GO | 58.7 ms | 5.13 T | **66%** |
| PyTorch | 52.4 ms | 5.74 T | **74%** |

**两边都跑到 58%，fp32 下已经没有"再快 1.5 倍"的空间** —— 这是物理限制，不是实现问题。

### 混合精度是唯一出路（已实测）

在真实训练脚本里给 PyTorch 版加 `--fp16`（autocast + GradScaler），同一模型、同一语料：

| 配置 | 单步 | 600 步后 loss |
|---|---|---|
| PyTorch fp32 | 52.4 ms | 0.0886 |
| **PyTorch fp16** | **40.6 ms（1.65×）** | **0.0886（完全相同）** |

⇒ 只要 TGAI GO 也做 fp16，按同样比例 `66.3 → ~40 ms`，
就比 PyTorch fp32 快 **1.65×**，同时满足原定 ≤45 ms 判据。
（PyTorch 自己也只有 1.65×，我们达到同一水平即算反超。）

**现状**：`cuda.py` 里 fp16 相关命中 **0 处** —— 需要新做 half 缓冲、cast 内核、
HGEMM/GemmEx 绑定、loss scaling。这是正在推进的独立工作流。

## 5. 融合的边界（原本以为的"反超路"）

> 先说结论：**融合只能追平，不能反超**。上一版报告把这条路当成反超手段，是判断错了。

## 5. 要反超，路只有一条：整层融合

现在瓶颈已不是 GEMM（只剩 4.9 ms），而是**每层约 30 个 elementwise kernel 及其反向**。
设计规格见 `fused_layer_plan.md`：

| 阶段 | 内容 | 预期 |
|---|---|---|
| P1 | 融合前向（RoPE + 在线 softmax attention + add） | ~26 ms（fp32 下最多 1.2×） |
| P2 | 融合反向（dRMSNorm + dGLU + dAttn） | ~20 ms（1.5×） |
| P3 | 整层一个 C 函数 | ~17 ms（1.85×） |

好消息：内核是 **NVRTC 运行时编译**，加融合核不需要构建系统（见 `fused_layer_plan.md` 末节）。

## 6. 一句话总结

- **要部署**：用 TGAI GO —— `.TG` 单文件、零依赖、模板内置、训练完直接上线。
- **要训练**：现在和 PyTorch 持平；等 P1–P3 做完再说"更快"，**在那之前不吹**。
- **要生态**：用 PyTorch。

---

## 7. 三条路都试完了：为什么还是没反超（最终账）

### C 路：融合/消除开销已到顶

一步的 host + kernel 启动成本（V100 实测）：

| 项 | 次数 | 耗时 |
|---|---|---|
| `_sgemm`（cuBLAS 调用） | 173 | 2.65 ms |
| `sgemm_strided_batched` | 80 | 1.59 ms |
| `launch`（所有 CUDA kernel） | 482 | 8.24 ms |
| **以上合计（host 侧）** | — | **~12.5 ms** |
| 整步 | — | **63.7 ms** |

⇒ **约 50 ms 是 GPU 真在算**，折合 4.7 TFLOP/s = **V100 fp32 峰值的 60%**。
派发开销已经被压到 ~12 ms，再融合只能从这 12 ms 里抠，**最多再省 3–5 ms**。

### B 路：混合精度的真实权衡（已实测）

| 配置 | 一步 loss | 梯度相对误差 | 600 步 loss | 单步 |
|---|---|---|---|---|
| fp32 基线 | 5.92568398 | — | 0.088538 | 66.3 ms |
| fp16（含长 K dW） | 5.92568588 | **1.97e-02** | 0.097645（+10.2%） | 55.5 ms（1.20×） |
| fp16（仅短 K，`k≤1280`） | **5.92568398** | **9.25e-07** | **0.088543（+0.006%）** | 66.0 ms（0.5%） |

**要么精度达标但没速度，要么有速度但精度不达标。** 这是一个真实的权衡，不是实现缺陷。
PyTorch 的 40.6 ms 来自「连 attention bmm / softmax / silu 都 fp16」（带宽减半），
那条路会把同样的数值代价扩大到更多算子。

### 最终结论（给用户的实话）

| 问题 | 答案 |
|---|---|
| fp32 能快过 PyTorch 吗？ | **不能**。两边都到 V100 fp32 峰值 58–60%，这是物理天花板 |
| 混合精度能快过吗？ | **能快 1.2×，但精度不达标**；要精度达标则速度归零 |
| 还有什么办法？ | ① 解决长 K 累加精度（分块累加 + fp32 中间和）后再上全 fp16；② 换 A100/H100（TF32/BF16 原生，改动小很多）；③ 换更大 batch/序列让 GEMM 更饱满 |
| 那 TGAI GO 现在的价值是什么？ | **部署侧**：`.TG` 单文件、零 Python 依赖、模板内置、训练完直接上线（见 §1） |
| 训练速度的诚实定位 | **与 PyTorch 持平**（1.01×），不是更快 |

### 交付清单（都已入库 + 桌面）

- 速度：4090 33.0 ms（1.05×）、V100 66.3 ms（1.01×）
- 两个考试：`pelican.TG`（6/6）、`chat10m.TG`+`.pt`（10.06M，loss 0.0885，引擎三问正确）

## ★ 2026-10-30 傍晚：CUDA Graph 落地，引擎首次真正反超

由 Grok 4.7 实现、父 agent 独立复验（同一台 4090、同一会话、600 步）：

| 配置 | ms/step | 说明 |
|---|---|---|
| 改前（无 graph） | 21.7 | 每步 484 次 kernel 启动，CPU 在关键路径上 |
| `TG_CUDA_GRAPH=0`（新代码） | 21.5 | 开关关掉无退化 |
| **`TG_CUDA_GRAPH=1`** | **18.9** | **−12.9%**，每步 0 次 Python 侧 kernel 启动 |

数值：首步 loss **逐位相同（5.925684）**，末 loss 0.088546（基线 0.088542，差 0.005%）。
捕获到 961 个图节点（348 次 cuLaunchKernel + 219 次 cuBLAS）；
AdamW 的 74 个节点每步用 `cuGraphExecKernelNodeSetParams` 更新 `bc1/bc2`。

### 与 PyTorch 的最终对照（4090，同代码、同语料、600 步）

| 对照方式 | TGAI GO | PyTorch | 结论 |
|---|---|---|---|
| **同能力（两边都组合式 RMSNorm）** | **20.8 ms** | 26.4 ms | **TGAI 快 1.27×** |
| 各自最优（默认） | **18.9 ms** | 27.1 ms | **TGAI 快 1.43×** |

> **意义**：此前"快 1.25×"被质疑是"torch 2.2.2 没有融合 RMSNorm"的版本红利。
> 把两边 RMSNorm 能力拉平后再比，**仍然快 1.27×** ——
> 这次不是版本红利，是**引擎本身真的更快了**（CUDA Graph + 前四轮优化之和）。

### 代价与限制（必须一并说）

- CUDA Graph 只在**固定 shape + 固定 batch**下成立；换形状要重新捕获（当前实现会回退）。
- 只在 4090 上验证；**V100 未验证**（产线机，未部署这套改动）。
- 训练脚本需按 `TG_CUDA_GRAPH=1` 显式开启，**默认关闭**。
