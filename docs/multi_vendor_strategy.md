# 战略记录：多厂商原生兼容（换赛道）

> 记录时间：2026-10-27
> 来源：JXW 口述（现场观察），我（DeepSeek）整理并标注「已证 / 待测」
> 状态：**待讨论**（用户说等他回来继续）

## 一、用户的核心观察（原话要点）

- 在 **海光 DCU（64 GB）** 和 **AMD MI300X（192 GB，魔搭提供）** 上用 PyTorch 训练 3B、1024 上下文时，
  **PyTorch 本身多占 40 多 GB 显存**，甚至容易 OOM。
- 对照：**CUDA 侧 48 GB 的 4090 就能完整全量训练 3B**，上下文还能到 1024。
- 推论：别的厂商为了兼容 PyTorch，要牺牲大量显存 → **CUDA 护城河越来越深**，
  因为其他厂商没有原生适配 PyTorch，PyTorch 也没原生适配别人的后端。
- 结论：我们自研训练引擎的**使命**是**原生适配国产卡与 AMD** —— 所谓"换赛道"。

## 二、显存税的四个来源（机制拆解）

| # | 来源 | 机制 | 证据等级 |
|---|---|---|---|
| ① | 缓存分配器 | caching allocator 只 reserved 不归还；`reserved - allocated` 可达数十 GB；ROCm 分配粒度更粗、碎片更重 | 机制确定，**量级待测** |
| ② | 注意力退化 | 后端无 flash/mem-efficient 实现时走 math 路径，物化 `[B,H,S,S]`；1024 上下文、32 头 = 每层 67–134 MB × 批 | 机制确定 |
| ③ | AMP 状态重复 | fp32 主权重 + fp16 权重 + fp16 梯度：3B = 12+6+6 = 24 GB；AdamW m/v 再加 24 GB ⇒ **48 GB 地板** | 确定（数学） |
| ④ | 后端库 workspace | rocBLAS / hipBLASLt workspace 不透明，可达 GB 级 | **待测** |

> 用户说的"40 多 GB"我**没有独立验证**（无那两台机器的数据）。
> 但 ①②④ 叠加在 3B/1024 上下文下，量级合理。

## 三、为什么这是结构性护城河

PyTorch 必须通用：
- autograd 不知道下一步算什么 ⇒ 只能保守保存中间量
- dispatcher 不知道你的内存布局 ⇒ 只能按算子分配

厂商要跑 PyTorch，就只能迁就这套抽象。**税是抽象层的税，不是硬件的税。**
CUDA 不吃这个税，是因为 PyTorch 就是围着 CUDA 长的。

## 四、我们凭什么能省（结构性优势，非优化技巧）

| 做法 | 省什么 |
|---|---|
| 自有内存计划（`src/tgai_memplan.c` 已存在） | 一次规划、按生命周期复用，无 reserved 空洞 |
| 手写反向、无 autograd 图 | 只存真正需要的张量，其余重算（checkpoint 是默认项而非插件） |
| 定点融合 kernel | 少物化中间量（rmsnorm+残差、SwiGLU、route+add 单一 kernel） |
| Muon 只存一阶矩 | 优化器状态 24 GB → 11 GB（对 64 GB 卡是生死线） |

## 五、必须承认的代价

1. 生态归零：无 HF、无 `torch.compile`、分布式通信要自己接（NCCL/RCCL 可用但要封装）。
2. 算子覆盖自己扛：GQA / MLA / 卷积等新结构都要重写。
3. "原生适配"要一张卡一张卡啃，各家 runtime 不同。

## 六、移植顺序（按机械性排序）

| 目标 | 路径 | 难度 | 说明 |
|---|---|---|---|
| **海光 DCU** | HIP | ⭐⭐ | DCU 属 ROCm 系，`hipify` 基本直过 |
| **AMD MI300X** | HIP | ⭐⭐ | 与 DCU 同一套代码 |
| **摩尔线程** | MUSA | ⭐⭐⭐ | CUDA 风格 API，改动中等 |
| 其他国产卡 | Vulkan | ⭐⭐⭐⭐ | 仓库已有 `build_vulkan.bat` + `third_party/vulkan` 雏形 |

**关键判断**：HIP 与 CUDA 的 kernel 源码几乎同构，真正要重写的是**运行时层**
（分配器 / stream / 事件 / 内存池）——而这层本来就该自己写，因为我们不吃 PyTorch 的抽象。

## 七、下一步（两个待办）

1. **先量"抽象税"基线**（可在 V100 上做）：
   同一 3B 配置（或缩比），A=PyTorch(fp16 AMP + AdamW) vs B=我们引擎(fp16+fp32 主权重+Muon+内存计划)，
   量 `peak allocated` / `peak reserved` / 每层激活峰值。
   **这是把"换赛道"从机制推理变成自证数据的第一步。**
2. **HIP 移植可行性验证**：把现有 7 组 kernel 用 `hipify` 过一遍，看编译错误量级，
   评估 DCU/MI300X 的真实工作量。
